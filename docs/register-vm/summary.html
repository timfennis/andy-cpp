Moving Andy C++ to a register VM

The plan is to replace the stack-based bytecode and its VM with a register-based one, to make programs run faster. Nothing else about the language changes: same results, same error messages.

Summary of docs/register-vm/plan.md, written 19 November 2026 as a plan and updated on 20 November with the result.

What a register VM is

Today's VM is a stack machine. To add two variables it copies both onto a stack, adds the top two, and copies the result back into a variable. A register machine gives every variable and every intermediate value a numbered slot in the function's frame, and each instruction names the slots it reads and the slot it writes.

Where we stand today

Two small programs, timed on your machine. Lua 5.4 and LuaJIT's interpreter are register VMs. Python is a stack VM with specialised instructions.

Why it is slow

I profiled the loop before deciding anything, because an earlier attempt to speed up the dispatch loop gained almost nothing and nobody knew why.

58machine instructions for each bytecode instruction. A tight interpreter needs 5 to 10.
43%of the samples are in pushing and popping the value stack.
0.001%of branches are mispredicted. Choosing the next instruction is not the problem.

So the cost is the stack itself. Every push and pop updates the stack's length in memory and moves a 16-byte value through a temporary. That is also why the earlier attempt didn't help: it made dispatch cheaper, and dispatch was never the expensive part.

What a prototype showed

I wrote the same loop for several small VMs in safe Rust, using a value type shaped like ours, with overflow checks and type checks. It is saved next to the plan so the numbers can be reproduced.

Two honest limits. The prototype is one loop of integers with no function calls, so it shows the best case. And other projects that made this move report 1.5 to 3 times faster on loops and arithmetic, but almost nothing on programs that spend their time inside the standard library. The WebAssembly interpreter wasmi got about twice as fast overall and saw no gain at all on recursive fib.

How the new VM works

Three ideas carry most of the design.

A call copies nothing

The caller puts the arguments in registers next to each other. Those same slots are the first registers of the function being called.

The compiler says where a value should go

Today every expression leaves its value on the stack, and a statement then throws it away. The new compiler passes a destination down: "put it in this register", "anywhere is fine", or "nobody wants it". A variable read costs nothing, because the variable already is a register, and a statement like f(x); never produces a value to discard.

The hot loop can't get out of step

The VM runs an inner loop over straight-line code with everything it needs in local variables, and leaves it only to enter or leave a function. Rust's borrow checker enforces that split. The earlier dispatch experiment had a bug of exactly this kind, where a stale position made the VM repeat a call forever and take 27 GB of memory. In the new shape that bug doesn't compile.

One rule to keep: an argument is a copy

++ appends in place when nothing else holds its left list, which saves a copy in chains like a ++ b ++ c. That is correct today only because reading a variable copies it onto the stack, so a list in a variable always shows two holders. A register VM that skipped that copy for arguments would give the wrong answer:

Casts used the same count to refuse a list that something else holds. You decided not to carry that over: the check is removed before the migration, the soundness gap it leaves around Any is one no real program hits today, and it gets a proper fix afterwards.

That also lets the VM stay simple about leftovers. A value that an instruction only looked at stays in its register until the register is reused or the function returns, so its memory is freed a little later and ref_count can read one higher. An earlier attempt to give CPython a register VM tried to clean these up with extra instructions and ended up slower than the stack VM, so the plan doesn't.

The risks the plan names, each with a guard:

  • A variable read too late. In x + { x = 5; x } the left side must be the old x. The compiler copies it first when a later operand can assign it.
  • The branch drifting from master. Ruby's version of this project fell a year behind. We merge master in weekly and avoid adding stack-VM instructions meanwhile.
  • Calls not getting faster. Expected at first. A direct call instruction and a smaller call frame are planned follow-ups.
  • Numbers that swing between builds. The same prototype code measured 1.8 s in one build and 2.8 s in another. Baseline and candidate are always built the same way and run interleaved.

Two things in the plan are my recommendations and not yet your decisions:

  • Register numbers are 16 bits wide. That avoids a limit of 255 values per function and measured the same as 8 bits. The thin slice in step 2 confirms it or falls back.
  • No new stack-VM instructions on master while the branch is open. Each one would have to be built twice.

The second of these was never needed: master didn't change while the branch was open.
